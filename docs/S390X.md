# s390x

ScarletNX builds for 64-bit IBM Z Linux (s390x), z13 and later. It is a secondary architecture: CI doesn't build it,
and support is the code and the preset below. No IBM Z machine has run it yet; [Building](#building) says what ran
under qemu-user.

## Building

The `linux-s390x-cross` preset cross-builds with Clang and LLD against a system root of the architecture, as
[MIPS64](./MIPS64.md)'s does. [gnu-cross](https://github.com/cross-tools/gnu-cross/releases)'s buildroot
(`s390x-ibm-linux-gnu.tar.xz`) is one: glibc in `s390x-ibm-linux-gnu/sysroot`, and GCC's runtime beside it, which
Clang takes from the folder `SNX_GCC_TOOLCHAIN` names. It carries no LLVM: `scripts/linux-llvm.sh` builds LLVM's
static libraries for the architecture, SystemZ its only code generator.

```bash
root=/path/to/s390x-ibm-linux-gnu
export SNX_SYSROOT=$root/s390x-ibm-linux-gnu/sysroot SNX_GCC_TOOLCHAIN=$root
scripts/linux-llvm.sh s390x .cache/llvm-s390x -- -DCMAKE_C_COMPILER_EXTERNAL_TOOLCHAIN=$root \
    -DCMAKE_CXX_COMPILER_EXTERNAL_TOOLCHAIN=$root
cmake --preset linux-s390x-cross -DLLVM_DIR=$PWD/.cache/llvm-s390x/lib/cmake/llvm -DSNX_LLVM_CONFIG=
cmake --build --preset linux-s390x-cross
ctest --preset linux-s390x-cross
```

The tests run under `qemu-s390x` with the sysroot as `-L`, and the ones that start a program of the target need a
`binfmt_misc` handler for it, as MIPS64's do.

What was run under qemu-user 10.0, against gnu-cross 20261001's buildroot with LLVM 23.1.3: the whole build, and the
test suite with a `binfmt_misc` of its own. Of 589 tests 463 pass in one run of them all, and `unit_cache` and
`3ds_extract` when run alone (four at once took them past their time); among them `elf_relocate` (s390x objects linked
into a module, loaded with `dlopen` and run), `native_recompiler`, `arm_module_chain`, the Linux runtime's `gnuabi_*`
but `gnuabi_elf32`, `cas128`, `endian` and `build_info`. What fails is what fails on big-endian
[MIPS64](./MIPS64.md#building), test for test, none of it in s390x-specific code: what needs the runtime JIT,
`llvm_fp_fast`, the `hookgen_refuses_*` tests, what qemu-user doesn't show as a machine would, the 3DS runtime's tests,
and the tests and runtime code that read or write guest words and lanes in the host's order.

## What differs from the other hosts

- **The baseline is z13.** Before it LLVM makes the runtime library's 128-bit shifts calls to libgcc's `__ashlti3`
  and `__lshrti3`, and a module links no library to have them. The recompiler builds a module for the host's CPU
  (z15 under qemu-user 10, which LLVM reads from `/proc/cpuinfo`), or for z13 where LLVM names none (`new_ir` in
  `src/common/cpu/recompiler/llvm/ir.c`).
- **STXP is CDSG**, the 16-byte compare-and-swap every z/Architecture machine has, inline once the pair's type says
  it is 16-byte aligned, as STXP's pair is: s390x's `__int128` is 8-byte aligned, which makes it a libatomic call
  (`snx_cas128` in `src/common/cpu/aarch64/helpers/integer.c`, `src/common/runtime/cas128.c`).
- **The module's code is PC-relative within 4 GiB**: a call (`brasl`, PLT32DBL), an address (`larl`, PC32DBL) and
  a GOT slot (GOTENT) reach any module, so its linker (`link_elf.c`, the relocations in `elf_object.c`) needs no
  veneers, and its GOT and dynamic relocations are x86-64's kind (`R_390_RELATIVE`). Its `.hash` has 64-bit words,
  as s390x's loaders read it (glibc's `Elf_Symndx`). Guest tail calls are LLVM's own jumps, to a function or through a
  pointer.
- **No runtime JIT.** The JIT loader's machines are x86-64, AArch64 and PowerPC64 (`HOST_MACHINE` in
  `code_loader.c`), so s390x runs only the code the AOT recompiler found, as RISC-V, LoongArch and MIPS64 do. LLVM
  has the code generator such a loader would need; the loader would need s390x's relocations, already in
  `elf_object.c`, and stubs for calls beyond 4 GiB.
- **Big-endian**, its guest values converted as big-endian PowerPC64's are
  ([Big-endian hosts](./PPC64.md#big-endian-hosts)), through the same code. Its pages are 4 KiB, jemalloc's too.
